先講結論：在半導體製造業評估 AI coding 工具，模型強不強反而是最後才比的。我會先問四件事：程式碼會去哪、誰核准、出錯誰負責、怎麼從一個人擴到一個團隊。

這篇是我目前的框架，不是成功案例。

## 1. 不只比模型

模型每幾個月就換一輪，今天最強的，半年後可能就不是了。真正會跟著工具很多年的，是這幾件事：

- **資料怎麼處理**：程式碼會不會被拿去訓練、保存多久、存在哪個區域。
- **能不能集中管理**：帳號、權限、使用紀錄，IT 看不看得到。
- **接不接得進現有流程**：IDE、版控、CI，還是要大家多開一個視窗複製貼上。
- **成本能不能預估**：按人頭還是按用量，用量暴衝時有沒有上限。

這四項過了，才輪到比誰寫的 code 比較好。

## 2. 沒核准的工具，不碰公司的程式碼

工廠的程式碼裡有製程參數、產品規格、系統架構。這些東西一旦貼進個人帳號的免費 AI，就收不回來了。

所以第一條線很簡單：沒核准的工具，不碰公司程式碼。個人帳號、免費方案，一律不行。

核准也不是一次就好。工具改了服務條款、換了資料保存政策，就要重新看一次。

## 3. AI review 不取代正式審查

AI 很適合當第一道篩子：抓明顯的 bug、漏掉的例外處理、命名不一致。這些人看久了容易眼花，AI 不會累。

但正式的 code review 還是人做、人負責。出了事，不能說「AI 說沒問題」。責任外包不出去。

我自己的流程是：先讓 AI 簡化程式、再讓 AI 找 bug，最後我自己看過 diff 才 commit。AI 幫我把雜訊清掉，判斷留給我。

## 4. 從個人 POC 到團隊試行

我不會一開始就全團隊導入。我的順序是：

1. **自己先用。** 在自己的專案上踩坑，搞清楚它擅長什麼、會在哪裡出錯。
2. **找兩三個自願的同仁試。** 選非關鍵的專案，出錯不會影響產線。
3. **先定好要觀察什麼。** 不是「省了多少時間」，而是哪類工作適合、哪類不適合、踩了哪些坑。
4. **寫成 checklist 再擴大。** 能寫成規則的才帶給團隊，寫不出來的就是還沒想清楚。

## 最後

AI coding 工具能不能進工廠，很少卡在模型夠不夠聰明，多半卡在這些界線有沒有先畫好。界線畫好了，它才有空間發揮。
